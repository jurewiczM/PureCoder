# Spec Contracts & Anchor Tests — Design

_2026-08-02_

## Problem

PureCoder's guards all assume the model may be wrong about *how* to write
something. None of them catch the model being wrong about *what* to write.

The checked-in `examples/portcheck/` output shows the failure exactly. The spec
said "raising ValueError on any non-numeric or out-of-range (1-65535) entry".
The generated `parse_ports` silently skips out-of-range ports instead of
raising. The code-blind tests, written from the same prose, encoded the same
misreading — so they passed. The loop reported success on the first attempt.

Every layer worked. The grammar constrained shape, the executor ran the code,
the test gate found the tests structurally sound. The answer was still wrong.

This is the one failure mode the architecture cannot currently see: **when the
writer and the tester share a misreading of the spec, verification reports
success**. For a tool in daily use that is worse than a red failure, because a
red failure retries and a false green ships.

The cause is the one the project already names: spec ambiguity, not the writer.
The tests never disagreed with the code because both were interpreting the same
ambiguous prose, independently and identically.

## Approach

Insert one artifact between the prose and everything downstream: a **contract**
— a structured, grammar-constrained statement of what the function must do.

Two things follow from having it:

1. The shared interpretation becomes a **single readable artifact** instead of
   an invisible agreement between two generated files. A `parse_ports`-style
   divergence becomes something the user spots in seconds.
2. Behaviour the spec states explicitly can be turned into **assertions
   generated by code, not by a model** — deterministic where the spec is
   explicit, model-generated only where it isn't.

This does not claim to make the contract correct. It makes the contract
*visible*, and makes the explicitly-stated parts mechanical. Those are
different claims and the docs must keep them apart.

## Architecture

```
description (prose)
      │
      ▼
  contract.py ── derive ──► contract JSON  (GBNF-constrained)
      │                          │
      │                          ├──► anchor_tests()  mechanical asserts, no model
      │                          ├──► writer prompt    (code generated against it)
      │                          └──► render()         "what I assumed" display
      ▼
  execute.py: anchors + designed tests ──► run_python ──► fix loop (unchanged)
```

The contract is derived once, before the loop. Every downstream consumer reads
that same structure. The executor, the fix loop and `lint_tests` are unchanged
— this feeds them better inputs rather than replacing them.

## Components

### `purecoder/grammars/contract.gbnf`

A third grammar alongside `env` and `makefile`, constraining output to the
contract schema. This fits the project's stated line — grammars are for config
shape, not code — because a contract is config-shaped. A malformed contract
becomes structurally impossible, not merely discouraged.

Schema:

```json
{
  "name": "parse_ports",
  "summary": "parse comma-separated ports",
  "params": [{"name": "s", "type": "str"}],
  "returns": "sorted list of unique int",
  "raises": [
    {"exc": "ValueError", "when": "non-numeric entry"},
    {"exc": "ValueError", "when": "port outside 1-65535"}
  ],
  "examples": [
    {"in": "'80,443'", "out": "[80, 443]"},
    {"in": "'99999'", "out": "raises ValueError"}
  ]
}
```

`in` holds a Python expression as text. `out` holds either an expression or the
literal form `raises <ExceptionName>`.

### `purecoder/contract.py`

| function | responsibility |
|---|---|
| `derive_contract(pc, description, max_retries=3)` | one grammar-constrained call, validated, retried with the error fed back — same loop shape as `generate_validated` |
| `validate_contract(obj)` | semantic guards past the grammar: `name` is a Python identifier, each `raises[].exc` is a valid identifier, `examples` is non-empty, required keys present |
| `anchor_tests(contract)` | contract → assertion source, mechanically |
| `render_contract(contract)` | contract → the human-readable "assumed" block |

`anchor_tests` emits two shapes:

```python
# {"in": "'80,443'", "out": "[80, 443]"}
assert parse_ports('80,443') == [80, 443]

# {"in": "'99999'", "out": "raises ValueError"}
try:
    parse_ports('99999')
    assert False
except ValueError:
    pass
```

Every generated assertion is `ast.parse`d before inclusion. A malformed example
is dropped with a warning rather than included — one bad example must not
poison the suite.

A `raises` anchor is emitted only when the exception name resolves to a
built-in exception. A custom exception class cannot be referenced from an
anchor, because the anchor is written before the implementation that would
define it; such an example is dropped under the same rule. Custom exceptions
still reach the test designer through the rendered contract, which can write
tests for them once the code exists.

### Two constraints worth stating explicitly

**`lint_tests` gates the designed portion only, never the combined source.**
Anchors are free assertions; counting them toward `MIN_ASSERTIONS` would let a
lazy tester through on the strength of tests it did not write. A gate that
rubber-stamps is the exact failure `validate_makefile`'s semantic guards exist
to prevent, and the same reasoning applies here.

**No new trust boundary.** Anchors execute in the same sandboxed subprocess
that already runs model-written code. The threat model is unchanged.

## Data flow

`generate_validated_python` gains two optional parameters. Defaults preserve
current behaviour exactly:

```python
generate_validated_python(pc, description, tests=None,
                          contract=None, use_contract=False, ...)
```

When `use_contract` is on:

1. Derive the contract, or accept one passed in. Accepting one keeps the
   function testable and lets a caller derive once and reuse.
2. Writer prompt = `description` + rendered contract.
3. `anchor_tests(contract)` produces the deterministic assertions.
4. The test designer receives `description` + contract, is told the anchors
   already cover the examples, and is asked for tests *beyond* them.
5. `lint_tests` gates the designed portion.
6. Final test source = anchors + designed tests, handed to the existing
   executor and fix loop.

The test designer stays code-blind. It reads the contract, never the
implementation.

### Call sites

- **`scaffold.py`** — passes `use_contract=True`. Only the code artifact is
  affected; the Makefile, `.env` and README paths are untouched.
- **`cli.py`** — a `--contract` / `--no-contract` pair. Resolution order, most
  specific first:

  1. an explicit `--contract` or `--no-contract` flag
  2. `PURECODER_CONTRACT` in the environment (`1`/`true` on, `0`/`false` off)
  3. the per-command default: on for `project`, off for `code`

  The env var exists so the `code` default can be flipped once the layer is
  trusted, without editing anything.

### Display

When a contract was used, the rendered block prints after the result: assumed
inputs, return, error cases, and which assertions were mechanical versus
designed. This is the artifact the user scans to catch divergence, and it is
the reason the whole layer earns its extra call.

## Error handling

Governing rule: **the contract layer must never make the tool worse than not
having it.**

| failure | behaviour |
|---|---|
| derivation fails validation after retries | warn, fall back to the no-contract path, continue |
| server unreachable during derivation | same fallback — one dead call must not kill the run |
| an example will not `ast.parse` | drop that anchor, warn, keep the rest |
| every example is malformed | no anchors; designed tests carry the run |
| contract is valid but wrong | not caught — surfaced by the display |

The last row is a documented boundary, not a gap to paper over. It belongs in
`docs/ARCHITECTURE.md` in the same register as the existing boundary notes: the
contract makes a wrong interpretation *visible*, which is a weaker and more
honest claim than making it correct.

## Testing

All model-independent, consistent with the existing 66 tests. No GPU, no
server.

- **`validate_contract`** — one test per guard: non-identifier name,
  non-identifier exception name, empty examples, missing required key.
- **`anchor_tests`** — equality shape, raises shape, malformed example dropped,
  custom (non-builtin) exception dropped, all-malformed yields empty, output
  always parses.
- **Flag resolution** — flag beats env var beats per-command default, both
  directions.
- **`render_contract`** — contains the fields a reader needs to spot
  divergence.
- **Integration via the existing `FakeModel`** — contract JSON queued as a
  response; assert anchors reach the executor, assert the gate sees only the
  designed portion, assert a derivation failure falls back cleanly.
- **Grammar** — `contract.gbnf` ships as package data and loads, the same check
  `env` and `makefile` already get.

Approximate size: ~200 lines of module, ~150 of tests, one grammar file.

## Out of scope

Deliberately excluded, still on the roadmap:

- `.env` semantic guard (the giant-rambling-comment gap in
  `examples/portcheck/.env`)
- Wiring RAG into the scaffolder
- tree-sitter chunking for non-Python code
- Model specialization via pruning and vocab-trim
